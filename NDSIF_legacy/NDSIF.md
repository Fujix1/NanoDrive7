# NDSIF — NanoDrive Serial Interface

文書版: 0.37 / Draft

更新日: 2026-10-14
対象: NanoDrive8（現行構成はESP32-S3、YM2151、OKI MSM6258）と追加論理音源の通信仕様

本書は PC と NanoDrive 間の演奏データ通信仕様をまとめ、実装・実測に合わせて更新するための文書です。即時制御 API v1 の受信・応答・YM2151 書き込みを実装済みです。ADPCM は第 4.4 節の byte 位置付きストリーミングを実装済みで、ユーザーによる実機確認で良好に動作しています。64µs tick の汎用チャンクは引き続き設計案です。

文書版0.37では、YM2203 の1個目・2個目、YM2413、YM3526、YM3812、YMF262、AY-3-8910 の1個目・2個目へAPIの対象を拡張します。これは仕様書の更新のみで、現行ND8の実装・ハードウェア構成・ホストcodecは変更しません。追加APIのwire形式と受信側のハードウェア正規化は第4.2.3節および `NDSIF_API.md` 第7.1～7.2節・第8節に定義します。

実装済みAPIと未実装の拡張仕様の独立リファレンスは `NDSIF_API.md`、人間がリアルタイム演奏する外部シンセ用の接続・待機・切断・エラー復旧手順は `NDSIF_HOST_GUIDE.md` を参照します。後者にはホストの運用規約と未実装の設計案を含みます。本書には特定の PC アプリの UI・ファイル解析・内部実装の詳細を記載しません。

## 1. 記述の位置づけ

- **要求**: これまでの相談で示された目的・制約。
- **設計案**: 実装候補。数値・形式・動作は検証後に確定する。
- **実装済み**: 現在の ND8 ファームウェアに存在する処理。
- **拡張仕様・未実装**: wire形式と動作規約を本書で定義するが、現行FWには追加しない機能。
- **未確定**: ホスト・デバイス双方の実装前に決める項目。

文書版と通信プロトコルのバージョンは別に管理します。文書版は通信上のバージョン番号を意味しません。第4.2節の既存APIと第4.2.3節の拡張仕様は形式を定義済みですが、実装状況は別に示します。それ以外の設計案にある名称は論理上の名称です。今回もwire版 `01` と既存のopcode・payloadを維持します。

## 2. 目的と要求

- Windows PC から USB シリアル経由で、YM2151 と MSM6258 の実チップを駆動する。
- 受信したタイミングをそのままチップへの書き込みタイミングに使用しない。
- 数 ms 分の演奏データを先行送信し、ND8 上の時間軸で再生する。
- MSM6258 のデータ書き込み要求後、約 10µs 以内の供給を目標とする。
- FM 書き込みと ADPCM の時間関係を保つ。
- PCM8 の合成と ADPCM エンコードは PC 側で行う。ND8 は合成済み ADPCM を供給する。
- 初版の ADPCM は 4 bit、1 byte に 2 sample を格納する。
- クロック、分周率、PAN、リセットを演奏データとともに制御できる構成を検討する。
- 接続開始・終了、通信途絶でのポップノイズを抑える。

PC 側の処理停止時間に上限が保証されないため、有限バッファで全ての途絶を吸収することは要求しません。途絶時の検出と復帰手順を定義します。

## 3. 役割分担

| PC / ホスト | ND8 / デバイス |
| --- | --- |
| 曲・演奏ソースの処理 | フレーム受信・検証 |
| PCM8 合成、必要な再サンプル・フィルタ | ADPCM・制御イベントのキュー管理 |
| ADPCM エンコードと状態の継続管理 | チップ要求割り込みによる ADPCM 供給 |
| FM 書き込み・制御イベントの時刻付与 | デバイス再生時刻に従う FM・制御イベント実行 |
| デバイスの消費量・空き容量に合わせた先行送信 | 再生位置・空き容量・エラーの通知 |

設計案では、受信・解析処理とチップ供給処理を分離します。OKI の供給 ISR は、検証済み・用意済みの 1 byte を取り出して書き込む短い経路とします。フレーム解析、CRC、メモリ確保、USB 応答、I²C 制御は供給 ISR 内で行いません。

## 4. 伝送とフレーム境界（即時 API は実装済み）

USB シリアルを双方向のバイナリ byte 列として使用します。PC の write と ND8 の read の境界は一致する前提にしません。

```text
0x00 + COBS(ヘッダ + ペイロード + CRC16) + 0x00
```

- 標準 COBS と前後の区切り `0x00` を使用する。連続する空の区切りは無視する。先頭の区切りは起動ログや未完フレームからの再同期用。
- CRC は CRC-16/CCITT-FALSE（poly `0x1021`、init `0xFFFF`、refin/refout false、xorout `0x0000`）。ヘッダ先頭からペイロード末尾までを計算する。`123456789` の CRC は `0x29B1`。
- 複数 byte 整数と CRC の格納は little-endian。
- ペイロード最大 256 byte、COBS 復号後最大 266 byte、COBS 部最大 268 byte、前後の区切り込み最大 270 byte。
- フレーム途中で最後の byte から 500ms 以上経過、または上限を超えた場合は、次の `0x00` まで破棄する。
- 不正 COBS、CRC 不一致、ヘッダ・長さ・バージョン不正は無応答で破棄し、チップを操作しない。
- プロトコル処理では生テキストログを出力しない。起動ログは残っているため、PC 側も不正フレームを破棄して次の区切りから解析する。

## 4.1. USB 接続監視と受信基盤（実装済み）

ND8 の現在の構成は `ARDUINO_USB_MODE=1` の Hardware CDC（USB Serial/JTAG）です。TinyUSB CDC の接続・DTR イベントと区別します。

- `Serial.isPlugged()` の SOF 監視結果を受信タスクで読み、USB リンクの接続・切断の変化を記録する。
- USB サスペンドやホスト停止も SOF が途絶えればリンクなしと見なされ得る。物理的な抜線だけを判定するものではない。
- `ARDUINO_HW_CDC_BUS_RESET_EVENT` を受け、再列挙・バスリセットを記録する。バスリセットを抜線と同一視しない。
- 現在の Arduino 実装には確実な COM ポート close 通知がなく、`isConnected()` も演奏アプリの接続状態を保証しない。
- 演奏アプリの接続確認は、今後の HELLO / SESSION と定期通信・タイムアウトで行う。無音とアプリ停止を区別できるメッセージを定義する。
- USB 給電のみの場合、抜線で電源も失われるため、切断後のミュート・通知などは実行できない。

ND6 と同様に `SerialMan::startSerialTask()` で専用受信タスクを起動します。受信リングからフレームを解析し、検証済みの即時コマンドを実行します。

| 項目 | 現在の実装 |
| --- | --- |
| Arduino USB RX キュー | 8KiB。`Serial.begin()` 前に確保。モード判定前なのでプレイヤーモードでも確保される |
| Arduino USB TX リング | 512 byte。起動前に確保し、空のときの利用可能容量を記録する |
| SerialMan 受信リング | 8KiB、内部 RAM。シリアルモード初期化時だけ確保 |
| 1 回の受信処理 | 最大 64 byte × 8 回。解析も最大 512 byte。その後 1 RTOS tick 待つ |
| 読み出し | `serialMan.read(data, size)`。NDSIF タスクのみが消費する（タスク mutex の取得待ちはあり） |
| 状態確認 | `serialMan.receiveStatus()`。リンク状態、未読量、受信・破棄量、接続・切断・バスリセット・溢れ回数、最終受信時刻 |
| 再開用の破棄 | `serialMan.clearReceiveBuffer()`。受信リングを初期化し、パーサ・送信待ち応答を受信タスクで破棄。次の区切りで再同期 |

受信 API はタスク用であり、OKI 供給 ISR から呼びません。これらは USB 受信基盤の容量であり、将来の ADPCM 再生キューやプリバッファ時間の確定値ではありません。

SOF 監視値の切り替わりは統計だけに記録し、受信リング・パーサを破棄しません。SOF が未検出でも実際に届いた byte は受信します。USB の実バスリセット時は受信リングを破棄し、検出時点で USB RX キューに残る byte も破棄します。再接続直後の初回メッセージも破棄され得るため、ホストは PING を再試行します。セッション ID による古いデータの識別は、将来の演奏チャンクで追加する予定です。

HWCDC の送信 ISR は SOF 未検出時に `IN_EMPTY` をクリアして送信リングを処理せず戻る経路があります。応答をドライバーに渡した後にこの経路へ入ると、一方向の演奏データ受信だけでは TX が再開しない場合があります。受信タスクは未送信 byte がドライバーの TX リングに残り、ハードウェア FIFO が空の場合、送信割り込みを再有効化して空 FIFO を flush し、既存の応答を送信へ進めます。応答の再生成やコマンドの再実行は行いません。

受信リングが溢れた場合は未読データと同じ受信処理中の残り byte を破棄します。その後パーサと送信待ち応答を初期化し、次の区切りから自動で再開します。`dataLost` は復帰時にクリアされますが、`overflows` は累積します。実バスリセット時もパーサと送信待ち応答を破棄します。SOF 監視値だけの変化では破棄しません。既に USB ドライバへ渡した応答が遅れて届く可能性があるため、要求番号も照合します。

溢れ回数は SerialMan のリングで検出したものです。Arduino の USB RX キュー内の欠落はこの API だけでは検出できません。CRC・長さを検証します。対話要求は応答を待ちますが、再生バーストと周波数設定には応答によるフロー制御を設けません。

## 4.2. 即時制御 API v1（実装済み）

今回の YM2151 書き込みはフレーム検証後に即時実行します。第 6 節以降の時刻付き演奏チャンクとは別の API で、この即時 API 自体は時刻同期・ADPCM 供給を行いません。ADPCM 併用時は第 4.4 節を使用します。ND6 の生コマンド列や VGM ファイルをそのまま送ることはできません。

COBS 復号後の形式:

| offset | byte 数 | 内容 |
| --- | ---: | --- |
| 0 | 2 | magic: ASCII `ND` (`4E 44`) |
| 2 | 1 | プロトコル版: `01` |
| 3 | 1 | コマンド ID。応答は要求 ID に `0x80` を OR |
| 4 | 2 | 要求番号。ホストが指定し、応答へそのまま格納 |
| 6 | 2 | ペイロード長（0～256） |
| 8 | 可変 | ペイロード |
| 8 + 長さ | 2 | CRC16 |

全応答のペイロード先頭は `00` = 完了、`01` = コマンド／引数の拒否です。エラー詳細はありません。正常な RESET に対する失敗判定は行いません。受信した応答 ID（bit 7 が 1）は無応答で破棄します。ヘッダ・CRC が正常な未対応コマンドには `01` を返します。

| 要求 ID | 名称 | 要求ペイロード | 応答ペイロード |
| --- | --- | --- | --- |
| `00` | RESET | 空 | `00`（リセット処理完了） |
| `01` | PING | 0～32 byte の任意値 | `00` + 要求の値をそのまま返す |
| `02` | GET_INFO | 空 | `00` + 本体名長 u8 + 本体名 + FW 版長 u8 + FW 版 |
| `03` | SET_OUTPUT_VOLUME | 最終出力の減衰量 u8（0～96） | `83`: `00`（処理完了）、不正引数は `01` |
| `54` | WRITE_YM2151 | アドレス u8、値 u8 の繰り返し。1～128 組 | 全組の書き込み完了後に `00` |
| `56` | WRITE_YM2151_BURST | `54` と同じアドレス・値の組 | 応答なし（不正引数の場合も無応答で破棄） |
| `57` | SET_CHIP_CLOCK | チップ ID u8 + Hz u32 little-endian（5 byte） | 応答なし |

**本体情報**: 本体名は UTF-8 の `NanoDrive 8`（11 byte）。FW 版は `ND_FIRMWARE_VERSION` を使用し、現在は `1.0b9`。文字列に NUL 終端は含めません。FW 版長は最大 63 byte。現在の応答ペイロードは `00 0B 4E 61 6E 6F 44 72 69 76 65 20 38 05 31 2E 30 62 39` です。

**リセット**: 先に `nju72342.mute()` でメイン出力をミュートします。YM2151 の IC、OKI の AC を既存の `FM.reset()` で操作し、レジスタキャッシュと OKI ソフトウェア状態を初期化、OKI に STOP を送ります。その後、曲データを消費しない `80` の無音ペアで OKI を駆動し、ミュート中に250ms安定待ちを終え、PAN・メイン出力のミュートを解除してから完了を応答します。起動時のシリアル初期化も同じ処理を使用します。無音駆動中の AUDIO_STATUS は未再生・位置0のまま、AUDIO_START で物理 PLAY を再発行せず曲データへ切り替えます。OKI 分周は 512、クロックは現在値を維持します（起動時 YM2151 4MHz / OKI 8MHz）。ESP32 自体は再起動せず、以降の要求を続けて受信できます。I²C 結果や実チップの読戻しによる成功／失敗判定は行いません。完了応答は準備・安定待ちを含むリセット処理が戻ったことを示します。

**YM2151**: フレーム全体が正常で、ペイロードが 2～256 byte の偶数長であることを検証してから、格納順に `FM.setRegisterOPM()` を呼びます。既存の PAN 反転設定とチャンネルマスクを適用し、アドレス・値の書き込み待ち時間を守ります。対話用 `54` の完了はソフトウェアからの書き込み完了を示し、実チップの読戻し確認ではありません。再生用 `56` は同じ検証・書き込み順序・待ち時間を守り、応答を生成しません。RESET の要求を最後のバーストの後ろへ送ると、その前の書き込みを処理してからリセットし、完了を返します。

ホスト手順:

1. COM ポートを開き、前後を `00` で囲んだ PING を送る。応答タイムアウトの初期値は 1 秒とする。起動待ちやバスリセットで破棄された場合は PING を新しい要求番号で再試行する。
2. 応答の COBS、magic、版、長さ、CRC、コマンド ID、要求番号を検証する。別の要求への遅れた応答は無視する。
3. GET_INFO で本体名・FW 版を確認し、必要なら RESET を実行する。
4. 制御要求（PING / GET_INFO / RESET）と対話用 WRITE_YM2151 (`54`) は 1 件ずつ応答を待つ。SET_CHIP_CLOCK (`57`) と再生用 WRITE_YM2151_BURST (`56`) は完了応答・受信確認を行わず、複数フレームをまとめて連続送信できる。PC は VGM の待ち時間を維持し、先の時刻の書き込みを早送りしない。
5. 要求番号は照合用であり、重複排除・再送保証ではない。同じ要求を再送すると再実行される。バーストは応答・欠落通知・再送を行わない。PING / GET_INFO は再試行可能だが、RESET / WRITE_YM2151 の応答が失われた場合は実行済みか判別できないため、自動再送しない。

切断による自動キーオフ、COM の開閉検出、接続状態の画面表示はこの API では追加していません。

## 4.2.1. SET_CHIP_CLOCK (`57`、実装済み)

応答なしの即時周波数設定です。ペイロードは必ず 5 byte とします。

| offset | byte 数 | 内容 |
| --- | ---: | --- |
| 0 | 1 | 論理チップID（既存ID 0～14は `t_chip` と一致） |
| 1 | 4 | 入力クロック Hz、u32 little-endian |

YM2151 に 4MHz を指定するペイロードは `05 00 09 3D 00` です。
要求番号 `0006` のフレーム全体は `00 06 4E 44 01 57 06 02 05 02 05 03 09 3D 03 66 E9 00` です。

| ID | チップ定義 |
| ---: | --- |
| 0 | `CHIP_NONE` |
| 1 | `CHIP_SN76489_0` |
| 2 | `CHIP_SN76489_1` |
| 3 | `CHIP_YM2413` |
| 4 | `CHIP_YM2612` |
| 5 | `CHIP_YM2151` |
| 6 | `CHIP_YM2203_0` |
| 7 | `CHIP_YM2203_1` |
| 8 | `CHIP_YM2608` |
| 9 | `CHIP_YM2610` |
| 10 | `CHIP_YM3526` |
| 11 | `CHIP_YM3812` |
| 12 | `CHIP_AY8910` |
| 13 | `CHIP_YMF262` |
| 14 | `CHIP_OKIM6258` |
| 15 | AY-3-8910 の2個目、拡張仕様で予約。現行 `t_chip` には未追加 |

YM2151（ID 5）と OKIM6258（ID 14）を実装しています。OKI は実クロック 4,000,000 / 8,000,000 Hz のみ受け付け、VGM の旧 OKI 正規化処理を通さず設定します。ADPCM 演奏中の変更は即時 `57` ではなく位置付きイベントを使用します。

- 不正な長さ、Hz が 0、未対応 ID、対象チップのクロックスロットが存在しない場合は何もせず、応答しない。
- 対象スロットは `ND::clockSlot[chip]` で取得し、`ND::freq` の範囲内であることを確認する。
- YM2151 は既存の `vgm.normalizeFreq(hz, CHIP_YM2151)` を使用する。3,375,000Hz、3,500,000Hz、4,000,000Hz は各既存設定へ、3,579,000～3,580,000Hz は既存の 3.579MHz 設定へ正規化する。他の非ゼロ値も既存処理と同様に 3.579MHz 設定へ正規化する。
- 正規化後の周波数が現在値と同じ場合、SI5351 呼び出し、チップ名更新、画面更新を全て省略する。
- 変更時は `ND::freq[slot]` を更新し、既存の `SI5351.setFreq(ND::freq[slot], slot)` を呼ぶ。`ND::chipNames` の該当項目を置換し、Player 表示中ならフッタだけを更新する。設定画面から戻った場合も現在の周波数を表示する。
- 周波数設定は受信順にレジスタ書き込みとともに処理する。完了応答、実チップの読戻し、I²C 成否の応答は行わない。

## 4.2.2. SET_OUTPUT_VOLUME (`03`、実装済み)

ペイロードは減衰量の u8 1 byte。NJU72342 のメイン出力 ch3/ch4 に同じ値を設定します。0 は減衰なし、1～95 は1dB刻みの減衰、96 はチップのミュート値です。入力ゲインや OKI の PAN 用 ch1/ch2 は変更しません。

要求の受信順で即時適用し、処理後に `83` / status=`00` を返します。長さが1 byte以外、値が97～255の場合は設定を変更せず、status=`01` を返します。完了はソフトウェア処理の完了を表し、I²C ACK・実出力の読戻しによる成功判定は行いません。

例: 12dB減衰は payload=`0C`、ミュートは `60`。設定値は RESET をまたいで保持し、リセット中の一時ミュート解除後も設定値へ戻します。シリアルモード起動時は0、再起動後の永続保存は行いません。時刻・ADPCM byte位置の指定や設定値取得APIはありません。未対応の旧ファームウェアは `83` / status=`01` を返します。

## 4.2.3. 複数音源レジスタ・クロック拡張（仕様定義・未実装）

既存のYM2151専用 `54` / `56`、ADPCM命令、chip ID 0～14を維持し、次を追加します。IDは論理音源を示し、物理スロットや搭載チップの種類をホストが指定するものではありません。

| 論理音源 | ID（10進） | wire（16進） | port |
| --- | ---: | --- | --- |
| YM2413 / OPLL | 3 | `03` | `00` |
| YM2151 / OPM、既存命令との同等指定 | 5 | `05` | `00` |
| YM2203 の1個目 / OPN | 6 | `06` | `00` |
| YM2203 の2個目 / OPN | 7 | `07` | `00` |
| YM3526 / OPL1 | 10 | `0A` | `00` |
| YM3812 / OPL2 | 11 | `0B` | `00` |
| AY-3-8910 の1個目 | 12 | `0C` | `00` |
| YMF262 / OPL3 | 13 | `0D` | `00` / `01` |
| AY-3-8910 の2個目 | 15、新規予約 | `0F` | `00` |

即時書き込みは `WRITE_REGISTERS` (`04`、応答 `84` / status) と `WRITE_REGISTERS_BURST` (`05`、拒否時も無応答) を定義します。payloadは `chip_id:u8 + port:u8 + (address:u8 + value:u8)[1..127]`、4～256 byteの偶数長。一つのフレームは一つの論理音源・portを対象とし、対象・port・長さ・AYのaddress `00`～`0F`を全体検証してから受信順に書き込みます。未搭載かつ互換割り当てもない対象は拒否します。YM2151は既存専用命令と同じPAN反転・チャンネルマスクを適用します。

ADPCMと共通の時間軸を使う場合は `59` kind=4 を定義します。payloadは `position:u32 + 04 + chip_id:u8 + port:u8 + (address:u8 + value:u8)[1..124]`、9～255 byteの奇数長。position・受信順・キュー件数・拒否時faultの規約は既存kind=0と同じで、レジスタ1組をキューの1件として数えます。既存kind=0のYM2151専用形式は変更しません。

クロックは既存 `57` の `chip_id:u8 + hz:u32` を維持して対象を追加します。**送信側は、物理OPL3でOPL1を鳴らす場合もOPL1のID・OPL1本来のHzを送ります。** 受信側が同種の物理音源を優先して解決し、必要ならOPL1→OPL2→OPL3、OPL2→OPL3、AYの各個体→対応するYM2203のSSG部へ割り当てます。機能を失う逆変換は行いません。

- OPL1/OPL2を物理OPL3へ割り当てる場合、受信側はOPL互換モードと4倍の物理クロックを設定します。論理OPL1の3,579,545Hzは物理OPL3の14,318,180Hz、4MHzは16MHzへ対応します。
- 論理OPL3はOPL3本来のHzを指定します。14,318,180Hzを再度4倍してはなりません。
- AYを物理AYへ割り当てる場合は1倍、標準のYM2203 SSG分周構成へ割り当てる場合は2倍です。AYの2MHzは物理YM2203の4MHzへ対応します。
- NDの搭載構成・分周・利用可能なクロック値への正規化は受信側の責務です。ホストはVGMヘッダーのdual-chipフラグや物理倍率をHzへ混ぜません。
- 論理音源が同じ物理チップやクロックスロットを共有する場合、レジスタ・クロックも共有し、最後の設定が有効です。独立した同時音源として扱いません。

倍率計算のu32オーバーフロー、未対応ID、互換割り当てなし、クロックスロットなし、実現できないクロック設定は適用しません。任意Hzの厳密な実現やクロック読戻しを保証するAPIではありません。`57` は無応答・即時設定であり、一般チップの位置付きクロック変更は追加しません。

現行FW `1.0b9` は `04` / `05` に未知要求の拒否応答 (`84` / `85`) を返し、追加対象の `57` を無視し、`59` kind=4 を不正kindとしてfaultにします。GET_INFOや既存の `5B` 成功は拡張対応の証明ではありません。拡張対応FW・構成が確認されるまでは、現行のYM2151 / OKI経路を使用します。詳細な形式と例は `NDSIF_API.md` 第7.1～7.2節・第8節・第10節を参照してください。

## 4.3. FM 送信の基本手順

- 接続時は PING → GET_INFO → RESET の応答を確認する。
- 必要なクロックを `57` で設定し、YM2151 のアドレス・値を最大128組ずつ、応答なしの `56` で送る。
- 初期化の完了確認が必要な場合は、先行する書き込みの後に一度 PING を送り、その応答を待ってから演奏を開始する。初期化の遅延を取り戻すために後続の演奏間隔を短縮しない。
- 即時 FM API は受信時に実行するため、ホストが送信時刻を管理する。通常のレジスタ書き込みごとに応答を待たず、書き込み要求を自動再送しない。
- 終了・停止時は必要な音止めと RESET を行い、完了応答を待つ。接続・待機・切断の詳細は第4.5節と `NDSIF_HOST_GUIDE.md` を参照する。

## 4.4. 常時駆動 ADPCM ストリーミング（実装済み・実機動作確認済み）

この拡張は、**連続 ADPCM 列の byte 位置**で FM・PAN・クロック／分周イベントを指定します。1 byte = 2 nibble、low nibble → high nibble の順です。第 6～11 節の 64µs tick 汎用チャンクとは区別します。位置は RESET からの単調増加 u32、自然周回を認めず、上限到達前にセッションを作り直します。

COBS/CRC/版番号/256 byte 上限は従来と同じです。`58`～`5A` は引数拒否時も無応答。エラーはラッチされ、`5B` で明示問い合わせします。古いファームウェアで誤って演奏しないよう、送信アプリは最初に `5B` の応答形式を確認します。

| ID | 内容 | ペイロード |
| --- | --- | --- |
| `58` | AUDIO_DATA | 先頭 byte 位置 u32 + ADPCM 1～252 byte |
| `59` | AUDIO_EVENT | 適用 byte 位置 u32 + kind u8 + kind 別データ |
| `5A` | AUDIO_START | 初期 OKI Hz u32 + 分周率 u16。事前に PCM を受信していること |
| `5B` | AUDIO_STATUS | 空。応答 `DB` は status `00` + 下記 u32 × 10 |

`59` の kind:

| kind | データ | 動作 |
| --- | --- | --- |
| 0 | YM2151 address/value 1～125 組 | 同一位置の FM 書き込みを受信順に実行 |
| 1 | OKI Hz u32 + divider u16 | Hz は 4,000,000 / 8,000,000、divider は 512 / 768 / 1024 |
| 2 | PAN u8 | 0:左右、1:左、2:右、3:左右オフ。既存 ND8 PAN 設定の左右反転も適用 |
| 3 | 終了後に繰り返す zero pair u8 | 指定位置 = 受信済み末尾。ゼロ PCM の末尾処理を済ませたエンコーダ状態に合う値をホストが渡す（`80` または `08`） |

イベント位置は同値を許す昇順。DATA 位置は受信済み末尾と完全一致が必要です。END は最後の DATA の後に送り、それ以降のデータ／イベント追加を禁止します。正常終了は END の位置到達で判定し、単なるキュー空を正常終了扱いしません。

`5B` の u32 は順に `accepted`, `played`, `pending`, `underflows`, `overflows`, `rejected`, `max pending`, `flags`, `late events`, `max event lag`。flags は bit0:開始済み、bit1:正常末尾到達、bit2:故障ラッチ。末尾到達判定には末尾データを供給した次の MCK が必要です。位置と遅延量の単位は byte。`late events` は 1 byte でも指定位置を過ぎたイベント数であり、その値だけで異常とは判断しません。RESET で全カウンタとキューをクリアします。

0.21 から flags の上位 bit に故障理由を追加しました。応答長 40 byte と bit0～2 は維持します。bit3:USB 実バスリセット、bit4:SerialMan 受信リングあふれ、bit5:明示的受信破棄、bit6:PCM 不足、bit7:PCM キューあふれ、bit8:イベントキューあふれ、bit9:引数／位置拒否。複数理由が重なる場合は OR。`overflows` は ADPCM/event キューの値なので、受信リングのあふれは `overflows=0` でも起き得ます。

### 4.4.1. 受信側

- 内部 RAM に PCM 4KiB とイベント 1024 件（12KiB）をシリアルモード時だけ確保。USB RX/受信リングとは別。
- 専用 MCK ISR が PCM を 1 byte ずつ供給。ファイル再生用 ISR/PCM8 ミキサーは使用しない。既存の level 3 GPIO サービスを共有し、NMI とは扱わない。
- PCM のコピーは割り込み禁止区間外。チャンク全体の格納後に末尾を公開。ISR は短いロック内で 1 byte を取得・GPIO 書き込みする。RESET は同じロックで供給を止め、出力ミュート中にハードウェアをリセットする。
- シリアルモードの GPIO ISR は `LEVEL3 | IRAM` で登録する。設定保存で Flash キャッシュが無効になっても、内部 RAM の音声リングから OKI へ供給を続ける。割り込みの停止で物理要求エッジを失う場合は、ソフトウェアの underflows に現れない点に注意する。
- FM・PAN・クロック／分周は受信タスクで供給済み byte 位置を見て実行する。I²C、描画、USB、メモリ確保は ISR で行わない。
- **制御イベントは指定境界ぴったりの実行を保証しない。** タスク周期、FM/I²C 待ち、描画の遅延がある。クロック・分周の変更もその間だけ旧設定で数 byte 進み得る。初回は遅延ログと実音で評価する。PCM 供給そのものは MCK 駆動。
- 周波数と分周を適用してからフッタを更新し、描画待ちを両設定の間に挟まない。
- データ不足、位置不整合、キューあふれ、輸送リセットを検出すると故障をラッチし、タスク側で OKI を PAN ミュート。追加 DATA では再開せず RESET が必要。
- 故障時の ISR は暫定的に `80` を供給する。これは正常な無音データではなく、ミュート後の常時供給用。**検出からタスクでミュートするまでの過渡ノイズは未解決**。通常の無音は下記 PC エンコードで処理する。
- CRC で落ちた DATA の欠落は次の byte 位置不一致または不足で検出する。イベント専用フレームの単独欠落を全て検出する連番／セッション管理は未実装。

### 4.4.2. ホストの供給責務

- 無音を含む連続した4-bit ADPCM列を生成し、出力エンコーダ状態を音符・チャンク・クロック変更をまたいで維持する。PCM8 等の合成はホストで行う。
- 1 byte は low nibble → high nibble の順で供給する。クロック・分周の変更イベントと、その設定で生成したデータの位置を一致させる。
- 演奏中は DATA / EVENT ごとの応答待ちを行わず、受信容量内で先行供給する。検証時の初期値は80ms先読み、約5.12ms/chunk。これは通信形式の固定値ではない。
- 開始前に FM 初期化と PCM / EVENT の事前供給を行い、必要なら PING で処理完了を確認してから START を送る。
- 無音区間も同じエンコーダ状態で符号付き PCM=0 を ADPCM 化して送る。音符ごとの実チップ STOP / PLAY は行わない。
- 正常終了時はゼロ PCM の末尾処理を行い、状態に合う zero pair を END に渡す。`80` / `08` を無条件に無音と見なさない。末尾到達を確認してから RESET を行う。
- STATUS による異常監視・先行量調整と長時間のクロックずれ補正はホストの責務。具体的な運用手順と未実装事項は第4.5節を参照する。

## 4.5. リアルタイム外部シンセのホスト運用

PC 側の YMFM 音源で既に動作している演奏入力・音色管理から、YM2151 レジスタ列と必要な PCM を NDSIF 出力バックエンドへ渡します。現在の wire は VGM に依存しません。PCM8 等の合成・リサンプル・12bit 化・ADPCM エンコードはホストで行い、ND8 は実チップへの供給だけを担当します。

| 場面 | 現行 API による手順 |
| --- | --- |
| 接続 | COM open → PING / GET_INFO → RESET 完了 → クロック・音色初期化。ADPCM 使用時は STATUS の対応確認、無音事前供給 → PING → START → 開始状態確認 |
| FM のみ待機 | ADPCM は開始しない。PCM の定期供給は不要。必要なら PING 監視 |
| 連続プロファイルの待機 | START 済みの OKI へ、符号付き PCM=0（中点）を同じ出力 state で ADPCM 化して継続供給 |
| 演奏 | FM のみなら即時 `56`。FM / ADPCM の共通時間軸では `59` を対応 `58` より先に送る。チャンクごとの確認は行わない |
| 離鍵 | 音源の release・キーオフ後も接続／連続供給を維持。ノート終了ごとに END / RESET を使わない |
| 正常切断 | 入力停止 → 連続プロファイルはゼロ末尾と END → 到達確認 → RESET 完了 → COM close |
| 緊急停止・fault | 古い生成・送信予定を止め、診断を可能なら保存。RESET とホスト状態再構築。通信不能なら音止めの完了は保証できない |

END 後は物理 OKI が無音を反復しますが、DATA / EVENT の再追加はできず、再開には両チップ RESET が必要です。通常のリアルタイム待機では END を送りません。FM 即時 API は ADPCM fault によって自動停止しないため、故障復旧は演奏全体を RESET します。

VGM 用の 80ms 先読みは操作遅延になるため、新しいリアルタイムホストの初期案は約 5ms チャンク・約 20ms 先行量とします。現在の VGM 実装の値は変更しません。20ms の安定性と、人間による演奏の latency は実機検証が必要です。

低頻度の STATUS を非同期で読み、長時間の PC / OKI クロックずれと fault を監視するホストを設計します。音源供給スレッドから同期的な応答待ち・送信完了待ちを反復しない構成とします。非同期受信・要求照合・ドリフト補正はリアルタイム UI 用の未実装事項です。

本体の COM close 判定、heartbeat timeout、通信途絶時の FM 自動キーオフ、SESSION / ownership、個別チップ RESET、一般 MUTE / ボリューム API は未実装です。現行 API の詳細な引数・拒否・診断形式は `NDSIF_API.md`、ホスト状態遷移・切断／復旧の具体的な順序は `NDSIF_HOST_GUIDE.md` に記載します。

## 6. 演奏チャンクの論理構成（設計案）

| 情報 | 用途 |
| --- | --- |
| セッション ID | 再接続・再開始前の古いデータを識別 |
| シーケンス番号 | 欠落・重複を検出 |
| チャンク開始時刻 | 演奏時間軸上の開始位置 |
| チャンク継続時間 | 区間の終端と先行量の計算 |
| ADPCM 先頭 byte 番号 | ストリームの連続性を確認 |
| ADPCM byte 数 | 供給量を指定 |
| イベント件数・データ長 | ペイロードの区切りと検証 |
| イベント列 | 時刻付き FM・チップ制御 |
| ADPCM 列 | 実チップへ順に送る連続データ |

イベントは「チャンク内の相対時刻、イベント種別、引数」で表します。イベントを時刻順に格納し、同時刻では格納順を使用する案です。具体的な配置と同時刻の実行規則は未確定です。

ADPCM データには byte ごとのレジスタ書き込みコマンドを付けず、連続した byte 列として格納する案です。ADPCM がない区間にも、FM イベントと時間の進行を表現できるようにします。

ADPCM 列と時間区間の対応、チャンク境界での未消費 nibble、空の ADPCM 区間、停止中の byte 番号の進行規則は実装前に確定します。byte 数だけから継続時間を決められるのは、対応する区間のクロック・分周率が定まっている場合です。

## 7. 時間軸（設計案）

- FM と制御イベントに固定単位の再生時刻を使う。
- ADPCM は連続した byte 番号も持ち、供給要求に合わせて消費する。
- 候補の時間単位は `1 tick = 64µs`（1 / 15,625 秒）。
- tick は通信上の時刻表現であり、64µs ごとのタイマー割り込みを必須としない。ADPCM の供給は実チップの要求割り込みを使う。
- 時刻の起点はセッション内に置く案とし、PC と ND8 の壁時計の一致を要求しない。
- FM も先行バッファと同じ時間軸で実行し、受信直後には実行しない。

4MHz / 8MHz と分周率 512 / 768 / 1024 の **byte 供給周期**は、64µs 単位で全て整数表現できます。

| OKI 設定 | sample / 秒 | byte / 秒 | 1 byte の供給間隔 | tick / byte |
| --- | ---: | ---: | ---: | ---: |
| 8MHz / 512 | 15,625 | 7,812.5 | 128µs | 2 |
| 8MHz / 768 | 約 10,416.7 | 約 5,208.3 | 192µs | 3 |
| 8MHz / 1024、4MHz / 512 | 7,812.5 | 3,906.25 | 256µs | 4 |
| 4MHz / 768 | 約 5,208.3 | 約 2,604.2 | 384µs | 6 |
| 4MHz / 1024 | 3,906.25 | 1,953.125 | 512µs | 8 |

初版は 2 sample（2 nibble）をまとめた byte 単位の供給を対象とします。nibble 単位の周期まで全て整数 tick になるわけではありません（8MHz / 768 の 1 sample は 96µs = 1.5 tick）。

FM イベントも 64µs 単位の時刻で指定し、指定時刻に従って実行します。約 1ms にまとめる処理周期は設けません。イベントがない tick に FM 書き込みを行う必要はありません。同じ時刻のレジスタ書き込みは格納順を保ち、チップの書き込み待ち時間を守ります。元の時刻からの丸め方と、同時刻の大量書き込みの扱いは未確定です。

チャンク約 5ms の候補は 80 tick = 5.12ms で、8MHz / 512 では 40 byte に相当します。他のレートでは byte 境界に合わせて時間・byte 数を調整します。40ms は 625 tick ですが、プリバッファ量は受信済みの完全なチャンク単位で満たします。

通信上の 64µs 刻みと、要求割り込み後の約 10µs 以内の供給目標は別の制約です。要求が発生したら次の tick を待たずに byte を送ります。

実チップの消費ペースと ESP32 のタイマーの差が長時間で積み上がらないよう、OKI の要求位置と FM の時間軸の同期方法を定義します。タイマー起点、位相補正、クロック変更前後の対応は未確定です。

受信フロー制御はホストとデバイスのペース差を扱いますが、それだけで ND8 内の FM / ADPCM 同期が解決するわけではありません。

## 9. ADPCM の連続性と無音区間

現在の第 4.4 節は 4 bit ADPCM、1 byte の下位 nibble → 上位 nibble の順で実装しています。以下はこの実装と、将来の汎用チャンクにも共通する連続性の条件です。

チャンクをまたいでも PC エンコーダの予測値・ステップ幅を継続します。実チップをリセットしないまま、チャンクごとにエンコーダだけを初期化してはいけません。初期状態と、実チップへのリセット / PLAY の対応は実機に合わせて確定します。

通常の無音区間は、PC が PCM ゼロを同じ連続エンコーダで ADPCM 化して送ります。現行 codec の符号付き 12bit（−2048～2047）で 0 は中点です。必要なフェードを導入する場合も PC 側の担当ですが、0.23 時点の良好な再生報告を受けて追加していません。第4.4節のOKIは、起動時・RESET中に符号化無音でデコードを準備し、STARTでホストの連続ADPCMへ切り替えます。END後も状態に合う無音を反復します。RESET後の準備用無音供給はホストのDATAを消費せず、ソフトウェア上の位置・runningは0 / falseのままです。

- `0x80` は一般的な PCM ゼロのコードではない。正負の差分による予測値・ステップ幅の変化がある。
- `0x88` を繰り返すと負方向に予測値が寄るため、無音用の固定値にはしない。
- ND8 が無断で補助 byte を挿入すると、PC エンコーダと実チップの状態がずれ得る。
- ミュートは音を抑える操作であり、ADPCM 内部状態の再同期にはならない。

通常の無音、正常終了、通信途絶による供給不足を区別します。

## 10. バッファとフロー制御（初期値案）

```text
sample / 秒 = OKI クロック / 分周率
byte / 秒   = sample / 秒 / 2
```

| クロック | 分周率 | sample / 秒 | ADPCM byte / 秒 |
| --- | --- | ---: | ---: |
| 8MHz | 512 | 15,625 | 7,812.5 |
| 8MHz | 768 | 約 10,416.7 | 約 5,208.3 |
| 8MHz | 1024 | 7,812.5 | 3,906.25 |
| 4MHz | 512 | 7,812.5 | 3,906.25 |
| 4MHz | 768 | 約 5,208.3 | 約 2,604.2 |
| 4MHz | 1024 | 3,906.25 | 1,953.125 |

| パラメータ | 初期値案 | 補足 |
| --- | --- | --- |
| チャンク時間 | 約 5ms | byte 境界に合わせる。最大レートで 40 byte = 5.12ms |
| 再生開始時プリバッファ | 40ms | FM・制御イベントも含めて受信する |
| 通常の先行量 | 約 40ms | チャンク時間とは別の値 |
| ADPCM リング容量 | 2KiB | 最大レートで約 262ms。通常は容量いっぱいまで貯めない |
| 受信・イベント用メモリ | 16～32KiB 程度 | イベント密度・実際の空き内部 RAM を踏まえて調整 |

この表は初期設計案です。第 4.4 節の現在の実装は PCM 4KiB・イベント 1024 件、VGM テストは 80ms 先読み。第 4.5 節のリアルタイムホストは約 20ms の先行量を新しい初期案として扱います。

これらは NDSIF の確定値ではありません。ファイル再生では 80～100ms、操作応答を優先する場合は 20ms 以下の先行量も比較します。

ホストは「PC 時間で 5ms ごとに 1 チャンク」と固定せず、ND8 の再生位置・受理位置・空き容量に基づいて送ります。STATUS は再生の進行に合わせて通知し、チャンクごとの往復応答を待たずに先行送信できる構成を検討します。

- 容量は byte 数とイベント数の両方で管理する。
- チャンク時間だけを基準に無制限に受信しない。
- 可変レートでは、残り byte 数と残り再生時間を区別する。
- ACK / STATUS の受理済みと、チップへ出力済みを区別する。
- フロー制御の単位、通知周期、再送、満杯時の拒否、重複処理は未確定。

現在の ND8 は内蔵 USB CDC を使用します。`Serial.begin(115200)` の指定を UART の転送帯域上限として扱いません。外付け USB-UART を使用する実装は別途条件を定めます。実効帯域は FM イベント・ヘッダを含めて測定します。

## 11. アンダーランと復帰（設計案）

「以後の ADPCM が意図的に不要」と「必要なデータが未到着」をプロトコル上で識別します。キューが空という条件だけで正常終了を判定しません。

異常時の初版候補:

1. アンダーランを記録し、OKI 出力をミュートする。ミュート完了までの供給方法も定める。
2. PC に再同期要求を通知する。古いセッションの続きをそのまま再生しない。
3. FM を含む演奏全体の停止 / 復帰位置を合わせる。
4. ミュート中に実チップと PC エンコーダを対応する初期状態へ戻す。
5. 新しいセッションでプリバッファし、出力が安定してからミュートを解除する。

期限後の再送だけでは ADPCM 状態を回復できません。遅着データの廃棄・保持、期限前の再送、供給を続ける補助 byte、復帰用プリロールの詳細は未確定です。

PLAY / STOP は出力電圧の遷移によるポップの懸念があります。現在は曲中・通常待機ではトグルせず、START の PLAY と RESET の STOP はミュート中に行います。本体側の自発的な故障通知・通信途絶時の FM 音止めは未実装であり、上記候補のすべてを実装済みとは扱いません。

## 12. 実装済みの基盤

- 設定がシリアルモードの場合、起動時にシリアル画面へ移行する。
- FM と OKI をリセットし、YM2151 は 4MHz、OKI は 8MHz に設定する。
- 初期化・RESET 時は OKI の STOP 後、ミュート中に符号化無音でデコードを開始して準備する。第 4.4 節の START で曲データへ切り替え、無音を含めた常時 PLAY を継続する。
- Player 画面でシリアルモードと USB 接続画像を表示する。アイコンは VGM 用を使う。
- 接続状態の画面表示は中止し、ラベルは「ベータ版 / Beta Version」に戻す。Hardware CDC と現在の書き込み方式を維持し、TinyUSB への変更は行っていない。USB リンク監視と受信 API は残す。
- システム名は表示幅を考慮して `YM2151 / M6258` とする。
- メニュー / 設定キーから設定を開き、プレイヤーモードへ変更・保存すると再起動する。
- シリアルモードでも本体の YM2151 CH1～CH8 キーでチャンネルマスクを切り替える。キー入力は既存の保留要求として受け、受信タスクで `FM.applyPendingChannelMask()` を毎周実行する。レジスタ受信・リセットと同じタスクで適用し、PAN 両側ミュート、解除時の最新キャッシュからの復元、LED 表示・消灯設定時の操作フィードバックには既存処理を使用する。マスク状態は既存処理と同様に RESET をまたいで維持する。
- YM2151 のアドレス・データ間の 4µs 待ちを GPIO クリティカル区間外へ移した。
- 待機中は YM2151 の CS を解除し、OKI に共有バスを譲る。YM2151 の対の書き込みは専用 mutex で直列化する。
- GPIO 共通 ISR サービスを入力登録前に確保する。モード設定を先に読み、シリアルモードでは `ESP_INTR_FLAG_LEVEL3 | ESP_INTR_FLAG_IRAM`、プレイヤーモードでは `ESP_INTR_FLAG_LEVEL3` を使用する。
- OKI は `GPIO_INTR_POSEDGE` と `gpio_isr_handler_add()` で登録する。NMI は使用しない。
- プレイヤーモードの既存 OKI 再生 ISR は PSRAM 上の曲データも読むため、IRAM フラグは付けない。シリアルモードの供給経路は内部 RAM のキューと IRAM/ROM の関数だけを使用する。
- 現在のシリアル起動経路はファイル再生用の OKI 初期化を呼ばない。USB 受信タスク・リング、NDSIF v1 のフレーム解析、PING / GET_INFO / RESET / WRITE_YM2151 / WRITE_YM2151_BURST / SET_CHIP_CLOCK は実装済み。シリアル専用の ADPCM 再生キュー・供給 ISR を第 4.4 節で追加。ファイル再生用の PCM エンコードタスクは起動しない。

入力 ISR も IRAM から直接登録する。Arduino の Flash 上の割り込みラッパーを通さず、エンコーダーは GPIO 入力レジスタを直接読む。2026-10-14 のビルド生成物で、11個の ISR/ドライバー/カーネル関数の IRAM 配置、6経路の直接呼び出し先が IRAM/ROM に収まること、7個の関連状態が DRAM に配置されることを確認した。実機での最大供給遅延・音質の保証は別途確認が必要。

### 通信・供給経路の確認事項

- RESET はメイン出力ミュート → FM / OKI リセット → OKI STOP → Visual 履歴初期化・表示中なら初期描画完了 → ミュート解除 → 完了応答の順に実行する。単に受信が止まっただけでは RESET しない。 RESET の表示初期化は保存済み初期フレームの再転送を使い、応答経路ではフォント・スプライトを再生成しない。
- USB の SOF 監視値の変化だけでは ADPCM を停止しない。実バスリセット、受信リングあふれ、明示破棄などは故障理由として区別する。実受信・パーサ・音声供給経路を結合したホスト上の5テストと、ADPCMの10テストが成功した。実機の最大供給遅延を保証するものではない。
- 常時駆動中は音源のブロックごとに実チップの PLAY / STOP を切り替えない。START の PLAY は PAN ミュート中、RESET の STOP はメイン出力ミュート中に行う。
- ユーザーから FM の開始同期修正後、および連続 ADPCM の入力停止・再開修正後に、シリアル再生が良好との報告を受けた。長時間ドリフト・全レート・異常切断の検証は別途必要。
- 受信レート表示は ADPCM 書き込みドロップの報告を受けて巻き戻された。原因は未確定で、現行ファームウェアに再適用していない。画面更新と供給の同時負荷は今後の測定対象とする。
